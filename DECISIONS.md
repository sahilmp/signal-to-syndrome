## Platform facts that affect both people

- **One job per code run.** A second `backend.run` in the same run fails with `ConnectionError … 'The code has already filed one circuit execution job; only one job is allowed per code run'`. Every bank configuration is its own run; the live-run button submits one job per press.
- **IonQ optimises abstract-gate circuits, even on the noisy simulator.** A repetition-code circuit whose CX controls start in \|0⟩ came back with zero detector events (P4, P8). **Submitting in native gates bypasses the optimiser and keeps the noise** (P9). All circuits that must show noise go through the native recipe in D1.
- **The Forte noise model has no readout (SPAM) error.** It only adds gate noise. Fine for us: readout is modelled classically in `src/core/readout/*`.
- **Each person owns their own Qollab project** (D10). Code moves only through GitHub.

Fingerprint (V9), checks, deviations and handoff notes:

- **Bank generator rules (from D1–D3, D7):** one configuration per run, selected by a variable at the top of the script; native recipe from D1; seed via `set_options`; output printed between `BEGIN_BANK` / `END_BANK`; provenance includes `backend.name`, `noise_model`, `sampler_seed`, `job_id`, native op counts and date.
- **Sanity check for every bank:** detector rate must be above 0 (P9, d=3 r=3 L0: 0.0325, events in 15.5% of shots). Zero means the circuit was optimised away.
- **Native transpile output** for d=3, r=3: `gpi2` 48, `ms` 12, `measure` 9 (the transpiler emitted `ms`, not `zz`; IonQ accepted it with forte-1).
- **CLAUDE.md rule 5:** the native recipe derives a backend from Qollab's own `backend` (same provider and credentials, no API keys), which we treat as within the rule. The wording was added to CLAUDE.md rule 5 on 6 Oct; confirm it at J2.
- **V9 fingerprint: `e80b58c8`** (Wed 7 Oct). `diagnostic(rep_d3_r3_L0)` from `src/core/sweep.js`, via `node tools/sweep.mjs --diag`: flat ε = 0.02, hard mode, seed 7, first 1000 shots, pGate calibrated on the whole bank. The Qollab page's Diagnostics hash must equal this once `src/ui/bridge_core.js` points to the real `sweep.js` (H5); the stub shows `stub0000`.
- **Deviation from the checklist (CC-A3 / C18 sweep.js spec), Wed 7 Oct:** the time-like edge of m[k][j] uses **p = xorP(pGate, pRead)**, not pRead alone (pRead = averageAssignmentError() in hard mode, pFromLlr(llr) in soft mode). Reason: gate errors on an ancilla also light vertical pairs, and `calibrate.js` already counts time-like edges as gate-noise edges. With pRead alone, time-like edges cost ~27.6 at ε = 0, so the decoder explained ancilla errors with space-like chains and pL at ε ≤ 0.01 was ~0.03 for every d (d = 7 worse than at ε = 0.12). After the fix, Stage 1 pL (hard, r = 3, L0 + L1 pooled, n = 8000) at ε = 0.005: d3 0.0044, d5 0.0013, d7 0.0001; at ε = 0.05: 0.0188, 0.0044, 0.0010. Locked by a test in `tests/sweep.test.js`. The checklists (execution checklist C18 line 864, team checklist CC-A3) still state the old rule; this row overrides them. Stages 2 and 3 inherit the rule through `runPoint`. The V9 hash is the same under both rules (the d = 3, ε = 0.02 decisions do not change).
- **Stage 1 checks (Wed 7 Oct), `data/results/stage1_flat.json`:** V1 PASS (flip rate 0.04936 [0.04842, 0.05032] at ε = 0.05, 200 000 draws). V5: bulk firing rate 0.048–0.053 for every r = 3 and r = 5 bank (0.020 for r = 1), pGate 0.0124–0.0139 (0.005 at r = 1). L0 and L1 firing-rate intervals overlap for every (d, r) except d = 7, r = 3: 0.0501 [0.0482, 0.0521] against 0.0533 [0.0514, 0.0554], about 6% apart (pGate 0.0130 against 0.0139). Each bank uses its own calibrated pGate, and the V6 logical error rates still overlap, so this is noted, not acted on. V6: L0 and L1 intervals overlap at every ε and d. Soft equals hard for the flat model (k = 80 of 4000 at ε = 0.05). No non-exact matchings.
- **Handoff to Person B (matching.js):** at ε = 0 every edge has the same weight, and tie-breaking toward observable parity 0 (see the V2 note) seems to inflate pL: d = 3 gives 0.029 at ε = 0 against 0.0044 at ε = 0.005 (d = 5 and 7 show a smaller rise). Only the ε = 0 point is affected; Stages 2 and 3 never have exactly zero readout error. Not changed; any tie-break change is a separate decision and may change the V9 hash (rerun `--diag` and update the row above).
