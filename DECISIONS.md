## Platform facts that affect both people

- **One job per code run.** A second `backend.run` in the same run fails with `ConnectionError … 'The code has already filed one circuit execution job; only one job is allowed per code run'`. Every bank configuration is its own run; the live-run button submits one job per press.
- **IonQ optimises abstract-gate circuits, even on the noisy simulator.** A repetition-code circuit whose CX controls start in \|0⟩ came back with zero detector events (P4, P8). **Submitting in native gates bypasses the optimiser and keeps the noise** (P9). All circuits that must show noise go through the native recipe in D1.
- **The Forte noise model has no readout (SPAM) error.** It only adds gate noise. Fine for us: readout is modelled classically in `src/core/readout/*`.
- **Each person owns their own Qollab project** (D10). Code moves only through GitHub.

- **Deviation from the checklist (CC-A3 / C18 sweep.js spec), Wed 7 Oct:** the time-like edge of m[k][j] uses **p = xorP(pGate, pRead)**, not pRead alone (pRead = averageAssignmentError() in hard mode, pFromLlr(llr) in soft mode). Reason: gate errors on an ancilla also light vertical pairs, and `calibrate.js` already counts time-like edges as gate-noise edges. With pRead alone, time-like edges cost ~27.6 at ε = 0, so the decoder explained ancilla errors with space-like chains and pL at ε ≤ 0.01 was ~0.03 for every d (d = 7 worse than at ε = 0.12). After the fix, Stage 1 pL (hard, r = 3, L0 + L1 pooled, n = 8000) at ε = 0.005: d3 0.0044, d5 0.0013, d7 0.0001; at ε = 0.05: 0.0188, 0.0044, 0.0010. Locked by a test in `tests/sweep.test.js`. The checklists (execution checklist C18 line 864, team checklist CC-A3) still state the old rule; this row overrides them. Stages 2 and 3 inherit the rule through `runPoint`. The V9 hash is the same under both rules (the d = 3, ε = 0.02 decisions do not change).
- **Deviation from the checklist (CC-A2 calibrate.js spec), Thu 8 Oct, agreed with Person B (B14 review, m1):** for **r = 1**, `estimatePGate` inverts the firing rate with **3 edges per detector**, P(fire) = (1 − (1 − 2p)^3) / 2, not 4. For r = 1 the only bulk layer is 0, and a layer-0 detector touches 2 space-like edges and 1 time-like edge (there is no round before round 0). r ≥ 2 keeps 4 edges (layers 1..r−1). Effect: the r = 1 banks (firing rate 0.020) give pGate 0.0066–0.0068 instead of 0.0049–0.0051. Only V5 uses the r = 1 banks; V9 (d = 3, r = 3) and every Stage 1–2 curve (r = 3) are unaffected by this change. Locked by tests in `tests/calibrate.test.js` (the r = 1 synthetic test now draws 3 edges; a closed-form test checks 3 edges at r = 1 and 4 at r = 3 for the same rate).
- **Deviation from the checklist (CC-A3 sweep.js spec, and CLAUDE.md Conventions), Thu 8 Oct, agreed with Person B (B14 review, M1):** `decodeShot` applies **idle errors to the true m, x before readout**, then measures. Before, it measured first, then flipped the hard bits and negated the llrs. With an asymmetric readout these differ: a dark ion flipped to bright must be read with the bright statistics, not as a dark reading with its llr sign flipped. Negligible in Stage 2 (idle flip ≤ 2.5e-5) but needed for Stage 3 (p_idle up to ~0.03 with T1 = 50 µs and τ up to 3 µs, and an asymmetric superconducting readout). The idle draws now come before the readout draws (made even when p_idle = 0, so readout draws line up across models), so every rerun changes: **V9 is now `53933f98`**, and Stages 1 and 2 were rerun (notes_results.md; numbers moved within their intervals). Locked by a boundary test in `tests/sweep.test.js` (p_idle = 1 against 0 with an asymmetric stub readout; it fails under the old order). The CLAUDE.md idle convention says the same (edited with this change, for Person B to approve).

- **Ion parameter card (A15, Wed 7 Oct), `params/ion.json`: lab values, not Forte values.** IonQ publishes no detection rates for Forte, so the four rates come from one published ¹⁷¹Yb⁺ experiment (same qubit species as Forte), [Crain et al., Commun. Phys. 2, 97 (2019)](https://www.nature.com/articles/s42005-019-0195-8). It was a surface trap with an SNSPD (system detection efficiency 4.356%), and it is the only source found that states all four rates as numbers. Values: R_bright 0.472 counts/µs (472 kcps), R_dark 4.2e-6 counts/µs (4.2 cps background), γ bright→dark 3.41e-4 /µs (341 Hz), γ dark→bright 1.64e-5 /µs (16.4 Hz). [Noek et al. 2013](https://arxiv.org/abs/1304.3511) and [Olmschenk et al. 2007](https://arxiv.org/abs/0708.0657) give these rates only in figures or as formulas. T1_idle = 1e7 µs (10 s), the low end of the 10–100 s that [Azure Quantum's IonQ page](https://learn.microsoft.com/azure/quantum/provider-ionq) lists for IonQ **Aria** (no Forte T1 is given there). tau grid 1–500 µs, covering 10.5–182 µs (Noek) and 11–500 µs (Crain), plus short times. Expected behaviour (rough estimate, before CC-A4): the bright error from pumping levels off at about 7e-4 from τ ≈ 20 µs; the dark error from background grows linearly (2e-3 at 500 µs); the idle flip probability stays below 3e-5 at every grid point, so no idle-driven optimum is expected (C1). **Computed curve (CC-A4, Thu 8 Oct), superseding that estimate:** belief-model average assignment error at nTh from `src/core/readout/ion.js` with this card, by τ (µs): 1: 0.31, 2: 0.19, 3: 0.12, 5: 0.047, 7: 0.019, 10: 4.9e-3, 15: 9.2e-4, **20: 5.9e-4 (grid minimum)**, 30: 6.5e-4, 50: 8.6e-4, 100: 1.4e-3, 200: 2.3e-3, 500: 4.8e-3. nTh = 0 up to 100 µs, 1 at 200 and 500 µs. So the readout error has an interior minimum near τ = 20 µs and then rises; it does not level off. The bright error does level off (8.0e-4 at 20 µs, 7.2e-4 at 100 µs, 1.4e-3 at 500 µs, where nTh = 1). The rise comes from the dark error, and that error is mostly dark→bright pumping, not background: 3.8e-4, 2.0e-3 and 8.1e-3 at 20, 100 and 500 µs, against 8.4e-5, 4.2e-4 and 2.2e-6 with γ dark→bright set to 0. So τPhys depends mainly on γ dark→bright (16.4 Hz), which should be in the Stage 4 sensitivity scan. Idle flip probability: 0.5 (1 − e^(−τ/T1)) ≤ 2.5e-5 at every grid point, confirming C1. The project page must say that the ion readout is a published lab setup, not a measured Forte characteristic. A PMT setup (lower collection, e.g. Noek: 2.2% efficiency) would make readout slower and is a candidate for the Stage 4 sensitivity scan.
